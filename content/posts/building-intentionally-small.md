# Curiosity — for the love of poking at things

I’m curious by nature. When I see something new — a term, a tool, an idea — I want to try it. Not because I need to master it, but because I want to understand it a little better. Often, that curiosity is sparked by something small: a post on social media, a prompt response in ChatGPT, or a concept I’ve never encountered before.

I enjoy making food for similar reasons. Trying new combinations doesn’t always lead to success, but it always teaches you something. TThose small bits of knowledge compound quietly over time. If you never try, you never get to know — and the gap between knowing and not knowing is often as simple as having experienced something firsthand.

Software engineering offers the same kind of opportunity. You can break things down to their most basic form and gradually experiment from there. You quickly learn that perfection isn’t the goal. What matters more is understanding why something works — and just as importantly, why it doesn’t. The experience of “this approach doesn’t work” is not failure; it’s essential.

Over time, I’ve realised that small, intentional actions sustained consistently add up far more reliably than single, all-consuming projects. That’s why I started MyLifeInDigital: to focus on small, focused pieces of work rather than chasing one “successful” outcome. The knowledge gained along the way is more valuable than any single finished project.

# For the love of Markdown

There came a point where I simply fell in love with the experience of working with Markdown in VSCode. It comes down to the simplicity of writing plain text with minimal formatting rules. Added to that is the fact that VSCode is a desktop app and works directly with local files on your hard drive. Somehow a browser-based WYSIWYG app never appealed much. 

Since Markdown is plain text with a simple convention, its adoption is almost universal. It’s everywhere — from Git repositories to tools like ChatGPT — and that ubiquity matters.

I have always desired an approach to publishing content using Markdown. IIdeally, I want something where I write Markdown, push it to Git, and it gets deployed. I do not want to edit Markdown content in a browser and I do not want to store Markdown content in a conventional relational database. Storing Markdown in a conventional relational database feels misaligned with what Markdown is. A Git repository, on the other hand, provides versioning, history, and a clear source of truth — all without additional infrastructure.

# Not just a Markdown renderer

From the outset my goal with MyLifeInDigital was not to simply build a Markdown parser and renderer. I don’t see it as a blog, but as a space where I can express ideas without being constrained to being a “Markdown blog”. That same curiosity is why I never saw MyLifeInDigital as “just a Markdown blog”.

Markdown is very well suited for HTML rendered content. The translation from Markdown to HTML is very well supported. Libraries like marked make it fairly easy to convert Markdown to HTML. I feel it’s important to highlight another key point: the conversion from Markdown to HTML should leave the original untouched. The reason Markdown is well suited to rendering in HTML is because the syntax is easily transformed.

# Starting point

You can use marked to parse to an HTML string. It works fine. Using the lexer, however, is more powerful. In the code below you can use `marked.lexer` passing in the Markdown content. You can read the content from a local file. 

The first step was simply to inspect what the lexer produces — not to transform anything yet, just to observe.

```typescript
function extractTokensUsingLexer(markdown: string): Token[] {
    return marked.lexer(markdown);
}

const __filename = fileURLToPath(import.meta.url);
const __dirname = dirname(__filename);

// Now resolve relative to the script location
const contentPath = "[content-path-goes-here]";
const content = readFileSync(contentPath, 'utf-8');
const tokens = extractTokensUsingLexer(content);
tokens.forEach((token, index) => {
    console.log(`${token.type.padEnd(12)}`);
});
```

The return type of `extractTokensUsingLexer` is an array of `Token`. A type provided in the marked package. The output from the code displays the token type. Each element in the abstract syntax tree (AST) has an associated token type. It is an important concept for later iterations.

## Why start here

At this stage, I’m not trying to build features.  
I’m trying to understand the shape of the problem.

Once content is represented as tokens instead of HTML, things like:
- custom layouts
- content-specific rendering
- metadata extraction

become much easier to reason about.

That’s for later. For now, understanding the building blocks is enough.

## What comes next

This is only the starting point.

For now, I’m intentionally resisting the urge to build features or abstractions too quickly. The goal is to spend a bit more time understanding the structure of the content itself — how it’s represented, how it can be shaped, and where flexibility naturally emerges.

The next step is to explore how these tokens can inform layout decisions and content-specific behaviour, without losing the simplicity that drew me to Markdown in the first place.

Slow progress. Small steps.  
But in the right direction.
